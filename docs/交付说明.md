# 交付说明 · 6 人协作手册

## 0. 这个项目的本质

**交付物全是 markdown + 脚本，没有业务代码。** 所以这不是编码比赛，是**上下文工程**比赛。
胜负手只有三个：skill 怎么切、规则怎么组织、上下文怎么省。

评分是**质量为主**，token 与用时为参考。子 skill 是内部实现细节——**评委只看主智能体的整体输出**。
因此：主智能体的输出质量 > 一切；子 skill 的"能独立答题"不是要求，**自包含只是打包约束**。


## 4. 三条铁律

### 4.1 定级只在 `sk_rules` 发生（契约 D2）

领域 skill 只对自己领域内的**原子风险点**定级。凡需跨维度交叉才能得出的结论
（申报收入 vs 流水、总负债 vs 年收入、抵押覆盖），一律**输出事实/因子**，判定上交 `sk_rules`。

**违反后果**：同一个客户会在 `sk_cash` 和 `sk_cred` 里被定成不同等级——致命评分硬伤。

### 4.2 规则只写进 `rules/rules.yaml`，绝不写进 skill 正文

各 skill 的 `references/rules.closure.md` 是**构建期自动生成**的，手工改会在下次构建时被覆盖。
需要新规则 → 加进 `rules.yaml`，重跑构建。

规则格式一行一条，短码表达式：

```
id|dim|cond|level|title|advice|basis|owner
R106|cash|loan_use_dev>0.3|高|资金用途偏离|核实资金真实去向|流水分析要点11|sk_cash
```

`cond` 里的变量**必须已在 `dict.yaml` 定义**，否则 `check_closure.py` 的 C4 会拦下。
需要新变量 → 加进 `dict.yaml`，走 P1 评审。

### 4.3 脚本承担确定性计算，模型只做判断

数字让模型算是三个损失叠加：**算错（质量）+ 慢（耗时）+ 贵（token）**。

所以：流水聚合、比率计算、规则求值、时序比对——**一律脚本**。
原始高基数数据（交易明细）**永不进模型上下文**。

---

## 5. token 控制：记住双重开销

子 skill 的输出回流主智能体时**付两次账**：生成一次 + 作为输入再算一次。

因此所有 skill 必须遵守**两层输出协议**（契约 IF-1.3）：

- **L1 摘要**（默认只回传这层）：`F|id|level|title|stage`
- **L2 证据**（留 skill 侧）：主智能体**仅在 `level=高`** 时按 id 索取

低风险 finding 的明细永远不进主上下文。
