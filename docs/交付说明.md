# 交付说明 · 6 人协作手册

## 0. 先搞懂我们在做什么

### 一句话

做一个 AI 助手，帮信贷员判断**农户贷款有没有风险**。

农户来贷款，信贷员要判断这个人靠不靠谱：材料齐不齐？流水正常吗？征信有没有问题？贷出去之后会不会还不上？

我们的 AI 就是干这个的。用户问一句话，它给出风险结论。

### 我们的东西是怎么组成的

想象成**一家银行网点**：

| 角色            | 是什么       | 干什么                               |
| ------------- | --------- | --------------------------------- |
| **主智能体**      | 大堂经理（分诊台） | 听客户说什么，判断该找哪个专家，最后汇总答复            |
| **5 个 skill** | 5 位专家     | 各自只管一摊：材料、流水、征信、风险规则、贷后           |
| **规则库**       | 一本风险手册    | 写着"什么情况算高风险"，比如"负债率超过 0.55 就是高风险" |

**最关键的一点**：我们写的不是代码，是**给 AI 看的说明书**（markdown 文件）+ **几个算数的小脚本**（Python）。

所以这不是编程比赛，&#x662F;**"怎么把说明书写得让 AI 又准又省"**&#x7684;比赛。

### 评分怎么算

- **主要看质量**——风险判断得准不准
- **次要看速度和花钱**——用多少 token、花多长时间

而且**评委只看主智能体最后给出的答案**。那 5 个专家 skill 是我们内部的实现细节，评委不单独看。

> 这条很重要，它意味着：专家的答案好不好不重要，**主智能体最终输出得好不好才重要**。

## 4. 三条必须遵守的规矩

### 规矩一：最终等级只能由 `sk_rules` 来定

**什么意思**：判断"这笔贷款整体是高风险还是低风险"，**只有 `sk_rules` 说了算**。

其他 4 位专家只能说"我这一摊发现了什么问题"，不能说"所以整体是高风险管理"。

**为什么**：

假设流水专家看到收入不稳定，说"中等风险"；征信专家看到负债高，说"高风险"。

那这笔贷款到底是中还是高？

如果没有统一裁判，**同一个客户在不同专家嘴里会得到不同结论**——这是致命的，评审一看就露馅。

所以规矩是：

> 专家只报**自己领域内**的问题。  
> 需要**跨领域**下结论的（比如"申报收入 8000，但流水只算出 4200"），  
> 专家只把两个数字交上去，**由 `sk_rules` 来判**。

### 规矩二：规则只能写在 `rules/rules.yaml` 里

**不要**直接去改 `skills/sk_cash/references/rules.closure.md` 这种文件。

那些文件是**打包时自动生成的**，你手改了，下次一打包就被覆盖，白改。

要加新规则 → 改 `rules/rules.yaml` → 重新跑打包命令。

规则长这样，一行一条：

```
id|dim|cond|level|title|advice|basis|owner
R106|cash|loan_use_dev>0.3|高|资金用途偏离|核实资金真实去向|流水分析要点11|sk_cash
```

意思是：**如果"用途偏离度"大于 0.3，就是高风险，问题是"资金用途偏离"，建议"核实资金真实去向"**。

`cond` 里用到的变量，**必须先在 `rules/dict.yaml` 里定义过**，否则检查会报错拦住你。

### 规矩三：算数交给脚本，AI 只做判断

**不要让 AI 去算数。**

比如"六个月平均收入是多少"——让 AI 算，它会算错，还慢，还贵。

正确的做法是：写个 Python 脚本算好，把结果告诉 AI。

> 算数是三个亏一起吃：**算错 + 慢 + 花钱**。

所以流水汇总、比率计算、规则匹配、时间序列比对，**全都用脚本**。

而且**原始的交易明细不要塞给 AI**。一千笔交易塞进去，又贵又容易看晕。  
脚本先算成"月均收入 17383，波动系数 0.79"这样几个数字，再给 AI 看。

## 5. 怎么少花钱：记住"两层输出"

这是省钱最关键的一招。

### 问题在哪

专家给大堂经理汇报，**同一段话要付两次钱**：  
一次是专家"说"出来的钱，一次是大堂经理"听"进去的钱。

所以专家说得越长，越贵——而且是双倍贵。

### 怎么办：先说结论，细节等他问

每个专家都准备**两份东西**：

**第一层：结论**（默认只交这个）

```
F|R106|高|资金用途偏离|贷前
F|R102|中|收入稳定性不足|贷前
```

**第二层：证据**（自己留着，大堂经理要才给）

```
R106|ev=cash.loan_use_dev=0.76|basis=流水分析要点11|conf=0.9
```

**规矩**：只有**高风险**的问题，大堂经理才会去要第二层细节。

中风险、低风险的细节，**永远不要往上交**——反正也没人看，白花钱。

## 6. 一个特别容易踩的坑：算不出来的时候不要填 0

**规矩**：算不出来的数字，填"空"（`None`），**绝对不要填 0**。

### 为什么？我们真的踩过

有一次测试，输入是**空的**（什么数据都没有），结果系统报出来：

> 「账户曾透支」高风险！  
> 「资金净流出」中风险！

**明明什么数据都没有，凭什么报风险？**

查了半天，原因是：

- "最低余额"算不出来，默认填了 `0`
- 而规则是"最低余额 ≤ 0 就是透支"
- **`0 ≤ 0` 成立，于是报了高风险**

"进出比"也一样，默认 `0`，"进出比 < 0.9 就是净流出"，又中招。

### 教训

`0` 这个数字**经常正好卡在风险标准的边上**。用它代替"算不出来"，就会凭空生成一堆假风险。

这种错误最可怕，因为它**不报错、不崩溃**，就是安安静静地给出错误答案。

所以现在有自动检查盯着这件事（`eval/contract_tests.py`），一旦退化输入报出风险点就会失败。
