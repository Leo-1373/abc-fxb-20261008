# 评测方案 · P6 工作手册

> 这份是**出题和打分**的规范。配套：`docs/分工.md`（P6 的任务清单）、`contracts/contracts.md`（输出契约）。

---

## 一、先把这件事想明白

### 为什么非要单独出题

如果我们自己写规则、自己出题、自己打分——**那一定全对，但毫无意义**。

评委手里有我们没见过的客户，他们会用那些客户来考我们。所以我们得**模拟那个场景**：找一批我们自己也没针对性地优化过的题，看系统能不能答对。

### 所以第一条纪律，也是最硬的一条

> **造题期间，不许打开 `skills/` 文件夹。**

不许看任何一位专家的说明书是怎么写的，不许看规则库里有什么规则。

只能看两样东西：
1. **赛题原文**（题目范围、考核要求）
2. **公开的业务常识**（农户贷款一般查什么、监管怎么规定）

为什么这么严？因为一旦你看了规则，你出题时会不自觉地"照着我们能识别的来出"，那些**我们根本没覆盖的风险**就永远不会出现在题里——而那恰恰是评委要考的。

### 一个现实提醒

这份规范里所有**格式和工具**是通用的，可以直接用。
但**正式题目的内容**必须来自赛题原文 + 你自己的调研，不能抄任何人现成的东西。

## 二、三档题，各考什么

| 档位 | 名字 | 考什么 | 数量目标 | 放在哪 |
|---|---|---|---|---|
| **L1** | 单元题 | 只考**一个**专家。比如只给流水，看能不能看出收入不稳 | 每个考点 3 道（正例+边界+反例） | `eval/cases/public/L1/` |
| **L2** | 单环节题 | 一个环节里的**多个**能力。比如贷前要同时看材料、流水、征信 | 20–30 道 | `eval/cases/public/L2/` |
| **L3** | 复合题 | **跨环节**、一次问好几件事 | 15–20 道 | `eval/cases/public/L3/` |

**L1 是地基。** L1 都答不对，L2、L3 不用看——所以先出 L1。

### 每道 L1 题必须凑齐三件套

这是最容易偷懒、也最不能偷懒的地方：

| 类型 | 什么意思 | 举例（流水维度） |
|---|---|---|
| **正例** | 数据里**确实有问题**，应该报出来 | 收入忽高忽低 → 该报"收入波动大" |
| **边界** | 卡在**及格线边缘**，看会不会误判 | 波动刚好在阈值上下，该报还是该放？ |
| **反例** | 数据**看着像有问题，其实是正常的** | 种粮农户春夏收入少 → **不该**报"经营中断" |

**反例最重要。** 漏报要扣分，**误报一样扣分**——好客户被当成高风险，业务上就是拒掉了一个好客户。

## 三、一道题长什么样

一道题 = 一个 JSON 文件。文件名 = 题号，比如 `L1-cash-001.json`。

```json
{
  "case_id": "L1-cash-001",
  "tier": "L1",
  "held_out": false,
  "dim": ["cash"],
  "stage": "贷前",
  "question": "帮我看下这个客户申请 10 万买农机，风险大不大？",
  "data": {
    "declared_inc": 18000,
    "purpose": "购买农机",
    "period": { "from": "2025-01-01", "to": "2025-06-30" },
    "txn": [ ... ]
  },
  "expected": {
    "risk_level": "高",
    "should_find": ["收入波动大", "交易对手集中", "资金用途偏离"],
    "should_not_find": ["账户透支"],
    "coverage_partial": false,
    "expect_clarify": false
  },
  "tags": ["正例"],
  "adversarial": false,
  "note": "单一合作社回款占七成，期中一笔建筑公司工程款用于购车。"
}
```

### 字段逐个说

| 字段 | 填什么 | 注意 |
|---|---|---|
| `case_id` | 题号，格式 `<档位>-<维度>-<三位序号>` | 全局唯一 |
| `tier` | `L1` / `L2` / `L3` | 必须和所在目录一致，工具会校验 |
| `held_out` | `true` / `false` | 必须和所在目录一致，工具会校验 |
| `dim` | 考的维度，从 `doc`/`cash`/`cred`/`x`/`ew` 里挑 | 可以多个（L2/L3 常见） |
| `stage` | `贷前` / `贷中` / `贷后` / `跨环节` | |
| `question` | **用户的原话**，不是你的描述 | 要像人说话，别写成测试用例标题 |
| `data` | 客户的原始资料 | 见下节 |
| `expected` | 期望答案 | 见下节 |
| `tags` | 自由标签，如 `正例`/`边界`/`反例`/`季节性`/`数据缺失` | 方便筛选统计 |
| `adversarial` | 是不是"坑题"（故意诱导误判） | 是就填 `true` |
| `note` | 出题人的备注，讲清这题想考什么 | **人工复核时全靠它** |

### `data` 里放什么

按题目的维度填，没考的维度就不填（**这本身也是一种考法**，见第五节）：

| 维度 | 字段 | 形状 |
|---|---|---|
| 流水 | `txn` | 交易数组，每笔含 `date` / `amt`（进账为正、出账为负）/ `counterparty` / `desc` / `channel` / `type` |
| 材料 | `doc` | 材料清单数组，每项含 `name`（名称）/ `present`（在不在）/ `expired`（过期没） |
| 征信 | `credit` | 逾期、负债、查询次数、担保等，字段名见 `eval/cases/public/L1/L1-cred-001.json` |
| 贷后 | `monitor` | 贷后监测记录：逾期天数、还款延迟次数、经营状态、是否联系得上等 |
| 其他 | `declared_inc` / `purpose` / `apply_amount` / `collateral_val` | 申请表上的基础信息 |

**数据要编得像真的**：金额量级合理，日期连续，对手方名称像真的对公主体（用"某 XX 公司"这种脱敏写法）。

### `expected` 里放什么 —— 这里有个关键决定

| 字段 | 填什么 |
|---|---|
| `risk_level` | 期望的总体等级，`高`/`中`/`低`。**拿不准就填 `null`**，表示"不考等级" |
| `should_find` | 应该识别出的风险点，用**业务大白话**，如 `"收入波动大"` |
| `should_not_find` | **不该**报出来的，如 `"账户透支"`（数据里余额明明一直是正的） |
| `coverage_partial` | 是否该标注"数据不全"。数据缺关键项时填 `true` |
| `expect_clarify` | 是否该**先追问**而不是硬答。关键信息缺失时填 `true` |

> ### ⚠️ 为什么 `should_find` 写大白话，不写规则编号
>
> 因为写规则编号（比如 `R101`）就等于**照着我们的规则库出题**——那就变成自己考自己了，
> 而且规则库里没覆盖的风险，你根本想不起来出。
>
> 写业务大白话（`"收入波动大"`）就没这个问题：**你只需要知道"这个客户收入不稳，业务上该提出来"**，
> 完全不需要知道我们内部是怎么编号的。这样出的题才是干净的。
>
> 至于"系统输出里写的是『收入波动异常』，大白话是『收入波动大』，怎么对上？"——
> 交给 `eval/synonyms.json` 同义词表去认，见第六节。

## 四、三档题各怎么出

### L1 单元题

**只给一个维度的数据，只考一个维度。** 别塞别的进去干扰。

出题套路：

- 先想一个**业务场景**：「种粮大户，收入集中在秋收后」
- 再想这个场景**业务上该得出什么结论**
- 再**反向构造数据**，让它精确落在这个场景上
- 然后**造两个对照**：一个"波动确实异常"的（正例），一个"波动刚好在边上"的（边界），一个"看着像异常其实正常"的（反例）

### L2 单环节题

**同一个环节，同时看多个维度。** 重点是看系统会不会**顾此失彼**——光看流水没看征信。

出题套路：给流水 + 征信 + 材料，让它们**互相印证或者互相矛盾**。
比如"申报月收入 1.8 万，但半年流水算下来月均只有 6000"——这就是**跨维度才对得出来**的问题。

### L3 复合题

**一句话问好几件事，或者跨环节。** 重点看**会不会漏掉其中一件**，以及**会不会跑错地方**。

出题套路：
- 「材料帮我审一遍，顺便看看流水和征信」——三件事，一件都不能漏
- 「这客户贷后有逾期了，你帮我查下他当初申请的材料」——**贷后的事里夹着"材料"两个字**，看会不会跑错到材料专家去

## 五、专门出"坑题"（至少 10 道）

坑题是**最容易发现问题**的地方。三个经典坑：

| 坑 | 怎么埋 | 正确答案长什么样 |
|---|---|---|
| **诱导跑错** | 问的是贷后，但话里带着"材料"这种别处的词 | 认出真正问的是贷后，别跑错 |
| **误报陷阱** | 季节性断档、正常的大额出账（买农机本来就贵） | **不报**风险，或只报低 |
| **数据缺失** | 故意少给关键字段（没给征信、流水只有 3 笔） | 标"数据不全"，**不许瞎猜** |

> 第三个坑最要紧。我们的血泪教训：算不出来的数字**填了 0**，结果凭空报出
> 「账户曾透支（高）」——因为 `0 ≤ 0` 正好落在阈值里。
>
> 所以这类题专门考：**数据不全时，是老老实实说"没数据"，还是硬编一个结论。**

### 还有一类题要出：反过来问

用户问的东西**本来就不该我们管**（比如问房贷、问企业贷）。
正确做法是**明确回复不适用**，而不是硬套农户贷款的规则。

## 六、打分怎么算

### 三个指标

| 指标 | 含义 | 扣分方向 |
|---|---|---|
| **漏报** | `should_find` 里该报的，没报出来 | 放过了一个风险 |
| **误报** | `should_not_find` 里的，报出来了 | 冤枉了一个好客户 |
| **等级** | 总体等级对不对 | |

**漏报和误报同等重要。** 别只顾着多报几个显得"敏感"——那是拿误报换漏报，一样扣分。

### 大白话怎么对上系统输出

系统输出的是正式的风险点名称（比如"收入波动异常"），题目里写的是大白话（"收入波动大"）。
中间靠 `eval/synonyms.json` 这张同义词表认亲：

```json
{
  "收入波动大": ["收入波动", "收入不稳", "收入稳定性", "收入波动异常"]
}
```

匹配规则很简单：**系统报出的名称里，只要包含这一组词中的任意一个（或者被包含），就算命中**。

> 这张表**需要 P6 校准**。跑第一轮的时候，工具会把"没认出来的"单独列出来给你看——
> 那些要么是系统真没报（漏报），要么是措辞不一样没认上。你一眼就能分辨，然后往表里补词。

### 为什么用工具跑分，而不是人工一道一道看

题一多，人眼看不过来，而且**前后标准会飘**（前面严后面松）。
工具跑出来的是**同一把尺子**，还能一眼看出"改了某个东西之后，是变好了还是变坏了"。

但工具只给**初判**。它认不出来的，会列成"待人工确认"清单——最后由你拍板。

## 七、held-out（藏起来的题）

### 规则

出完题之后，**挑 20% 单独放到 `eval/cases/heldout/`**。

| 放哪 | 谁能看 | 什么时候用 |
|---|---|---|
| `eval/cases/public/` | 全队都能看 | 平时开发、调试，随便跑 |
| `eval/cases/heldout/` | **只有 P6 能看** | 只在最后验收时用 |

### 为什么非藏不可

如果写规则的人和出题的人看同一套题，写规则的人会**不自觉地针对这些题**做优化。
等评委拿出不一样的题，就露馅了——这叫**过拟合**。

### 藏的办法

- 目录上物理隔开（放在 `heldout/` 里，不跟公开题混）
- 文件里 `"held_out": true` 双重标记，工具会自动核对一致性
- 平时跑分加 `--public-only`，**默认不碰 held-out**

## 八、怎么用工具跑分

```bash
cd abc-fxb-20261008

# 1) 看题库概况（有多少题、各档位分布、held-out 比例）
PYTHONIOENCODING=utf-8 python3 eval/runner.py --list

# 2) 只检查题目本身有没有写错（不调系统，纯校验）
PYTHONIOENCODING=utf-8 python3 eval/runner.py --check

# 3) 用跑好的系统输出打分
PYTHONIOENCODING=utf-8 python3 eval/runner.py --score eval/out

# 4) 只跑公开题（默认就是这个），加上生成报告
PYTHONIOENCODING=utf-8 python3 eval/runner.py --score eval/out --report eval/out/report.md
```

### 第 3 步里的 `eval/out` 是什么

**这是关键设计**：跑分工具**不负责去调用系统**——因为系统怎么调用，现在还不确定（P1 的平台侦查还没做完）。

所以中间隔了一层**文件**：

```
你把系统对每道题的回答，存成一个文件
    → 文件名就是题号：eval/out/L1-cash-001.json
    → 工具读这些文件来打分
```

这样做的好处：

| 好处 | 说明 |
|---|---|
| **不受平台影响** | 平台定下来了，只要写个小脚本把回答落成文件就行，打分工具一个字不用改 |
| **回答可以人工改** | 想试"如果这里报对了会怎样"，直接改文件重跑 |
| **打分可复现** | 同一批文件，跑多少次结果都一样 |

文件内容（最简形式）：直接放主智能体的最终输出就行。
想统计花了多少 token / 多少时间，就多包一层：

```json
{
  "output": { ...主智能体的最终输出... },
  "usage": { "tokens": 1234, "seconds": 12.3 }
}
```
