## B1 · 贷后数据：`monitor` 还是 `monitor_ts[]`？

**不只是改个名字——形状不一样。**

| 出处 | 声明 |
|---|---|
| 题目 `L1-ew-001` / `L3-x-901` | `monitor`：**单个对象**（快照），槽里是 `monitor_date` / `overdue_days` / `biz_status` / `contact` … |
| `skills/sk_ew/skill.md` frontmatter | `input_slots: [monitor_ts[], signals, loan{}, stage]` |
| `contracts/contracts.md` **IF-3**（冻结接口） | `monitor_ts[]`：**时点数组**，每项 `{date, overdue_days, balance, repay_delay_cnt, use_dev_flag, biz_abnormal, contact_fail, natural_disaster, price_shock, guarantee_deplete}` |

**为什么必须吵清楚，不能各让一步**：`sk_ew` 存在的全部理由就是**时序**——
信号在连续 ≥2 个时点出现才升级、最近 2 个时点消失才算拟解除。给它一个单时点快照，
这个 skill 就退化成 `sk_rules` 的快照判定，**没有存在价值**。

**建议**：以 IF-3 为准。题目改成时点数组；`L3-x-901` 尤其要给 **≥2 个时点**，
否则"升级/解除"根本没东西可考。

**怎么验**：

```bash
PYTHONIOENCODING=utf-8 python eval/runner.py --check --include-heldout
# 现在会硬失败并指出这两道题，exit=1
```

### 📌 P3 提案（真超奇，2026-10-09）—— 采纳 IF-3，但要连"形状"一起改

同意以 IF-3 为准。**但只把 `monitor` 改名成 `monitor_ts` 不够**——现在既不是数组，字段名也对不上，

三点补充：

1. **`bal_drop` 不能由题目直给。** 契约与 `dict.yaml` 定的口径是
   `(上期余额-本期余额)/上期余额`。题目再给一个数就有了两套口径，迟早对不上。
   **单时点题本来就不该考"余额下降"**——那必须有两个时点才能算。
2. **描述字段值得进契约。** 赛题硬要求「**自然因素**和**市场因素**必须各有题，
   而且**要能分得清**，不能把行情下跌误判成天灾」（`docs/赛题原文.md` §三·5）。
   纯布尔值只能表达"发生了"，**表达不了"发生的是什么"**。建议契约加：
   `natural_disaster_desc` / `price_shock_desc`（字符串，可空）。
   **但规则求值只认布尔值**，描述字段是给模型看理由的，不参与 `cond`。
3. **`L1-ew-001` / `L3-x-901` 至少要给 2 个时点。** 单时点考不出升级/解除/跨档，
   而"信号在连续 ≥2 个时点出现才升级"是 `sk_ew` 存在的全部理由。
   `L3-x-901` 作为复合题更是必须给——否则这道题在原理上考不到贷后时序。
   `L1-ew-001` 现在单时点，虽然"专考市场因素"那个意图是达成的，
   但**顺带考不到任何时序能力**，建议补一个时点。

### 📌 P3 提案（真超奇，2026-10-09）—— 取超集，题目只需加一个 `type`

先说时序：这条写在我**已经补完 `check.py` 之后**了，所以只能定形状、再回头对齐脚本，不是"先说后做"。
不过下面的提案**向评测方案靠**，题目改动量最小。

建议 `doc[]` 每项定为**评测方案 `{name, present, expired}` 的超集**：

```
{ type, name, present, expired, no, issue_date, expire_date, holder, fields{} }
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `type` | **是** | **规范短码**，取值见 `必备材料清单.md` §1–§3 第一列（如 `ID_CARD`）。规则与脚本按它匹配 |
| `name` | 否 | 展示用中文名；缺省时脚本按 `type` 反查清单 |
| `present` | 否 | 保留评测方案的语义。**`false` 的项不要放进 `doc[]`**——放进去等于"交了"，脚本会按已交处理 |
| `expired` | 否 | 保留。给了 `expire_date` 时**以日期为准**，`expired` 只做交叉校验 |
| `fields{}` | 否 | 一致性比对用原始值：`{name, id_no, area, amount, sign_date, seal_count}` |

**为什么非加 `type` 不可**：`{name, present, expired}` 三个字段**表达不了跨材料矛盾**，
而"同名同证号的材料互相对不上"是 `doc` 维度一半的判定力（`doc_inconsist_cnt` 及其规则 R004/R008）。
没有 `fields{}`，`check.py` 里那半段逻辑就是死的。

**为什么 `type` 不给 `name` 顶替**：`name` 是自由文本（"身份证"/"借款人身份证"/"身份证复印件"都能写），
拿它做匹配会**静默漏配**——漏配的表现是"没报缺件"，而不是报错，属于最难发现的一类错误。
`type` 是枚举，对不上就是显式的 `unknown`，脚本会把它列出来（见 `必备材料清单.md` §8）。

**题目要改的地方**：每项把 `name` 的**规范码**补成 `type`，其余原样保留即可。
需要考"材料互相矛盾"的题，再加 `fields{}`。

> 我的 `skills/sk_doc/scripts/check.py` 已按 `{type, ..., fields{}}` 写好；
> 若最终裁决用别的形状，改的是我这边，**题目只需按上表补齐 `type`**。

**这三条的共同病根**：题目数据（钱浩军）和 skill 输入契约（各 skill 作者）是**两个人分头写的**，
谁也不知道对方用了什么名字。名字对不上时 skill 取不到值 → 规则不命中 → **分数照扣，但全程不报错**。
架构在规则层解决了"拼不起来"，**在题目数据层又长了一遍**。
所以那道键名校验不是一次性补丁，是这一类问题的**长期拦截点**。
