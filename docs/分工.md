# 第一部分：先把几个关键概念讲清楚

在分工之前，必须先搞懂三样东西。不然后面说的任务你会不知道在干什么。

## 一、规则库是什么？为什么要扩容 52 → 200+？

### 它是一本"如果…就…"的手册

我们的系统判断风险，**靠的不是 AI 的感觉，而是这本手册**。

规则库里一条规则长这样（就是一行字）：

```
R106|cash|loan_use_dev>0.3|高|资金用途偏离|核实资金真实去向|流水分析要点11|sk_cash
```

竖线分开的每一段分别是：

| 位置 | 内容                 | 读作                  |
| -- | ------------------ | ------------------- |
| 1  | `R106`             | 规则编号                |
| 2  | `cash`             | 属于流水这一摊             |
| 3  | `loan_use_dev>0.3` | **如果**"用途偏离度"大于 0.3 |
| 4  | `高`                | **那么**判定为高风险        |
| 5  | `资金用途偏离`           | 这个问题的名字             |
| 6  | `核实资金真实去向`         | 建议怎么办               |
| 7  | `流水分析要点11`         | 依据出处                |
| 8  | `sk_cash`          | 由哪个专家负责             |

### 系统是怎么用它的

客户来贷款，系统做的事就是：

1. 从材料/流水/征信里**算出各种数字**（收入波动系数、负债率、多头家数……）
2. 拿这些数字**逐条比对这本手册**
3. 比中了，就报出来："发现高风险——资金用途偏离"

**所以：手册里没写的风险，系统就识别不出来。**

### 为什么必须扩容

现在的 52 条，只覆盖了**最常见**的情况。而评审的题里会出现各种花样。

举个真实的例子，我们现在的流水规则里**没有**这一条：

> **农业有季节性。** 种粮的农户，秋收后才有钱进账，春天和夏天流水很少甚至没有。  
> 我们现在的规则 `R103：断档月数 ≥ 3 → 中等风险` 会把它误判成"经营不连续"。

但这是**正常现象**，不该报风险。正确做法应该加一条能识别季节性的规则：

```
R1xx|cash|gap_cnt>=3 && industry!="季节性农业"|中|经营连续性中断|...
```

**这就是扩容的意义。**

### 两个方向都会扣分

- **漏报**：手册没写 → 真有风险但没识别出来 → 扣分
- **误报**：手册写得太粗 → 好客户被当成高风险 → 一样扣分

所以扩容**不是简单地堆数量**，而是要覆盖更多**真实存在**的风险情形，同时避免误伤。

### 规则从哪来？

不用凭空想。四个来源：

1. **赛题原文**——它提到的痛点就是考点
2. **监管文件**——银保监会对农户贷款、涉农信贷的规定
3. **农行信贷制度**——行内的农户贷款管理办法、尽职调查要求
4. **公开的农户贷款风险案例**——搜"农户贷款 风险 案例 骗贷 挪用"

> 调研这件事**完全不需要懂技术**，会查资料就行。真超奇/严军超/邱家杰的第一件事都是这个。

### 规则多了会不会很贵？

不会。这就是我们之前设计"规则切片"的原因：

- 规则一行一条，200 条约 5k token（比写成散文省 3 倍）
- 打包时**按专家切分**：`sk_cash.zip` 里只有流水那几十条，不是全部 200 条
- 运行时**按需读取**：不需要时不读

**所以你尽管写，不用担心把系统撑爆。**

## 二、skill.md 是什么？

就是**给 AI 看的说明书**。

AI 不知道"农户贷款要查哪些材料"。你得写一份说明书告诉它：这个专家负责什么、收到什么数据、按什么步骤做、输出什么格式、什么情况不归它管。

一个 skill 文件夹长这样：

```
skills/sk_cash/
├─ skill.md              ← 说明书（主文件）
├─ references/           ← 参考资料，需要时才读（比如详细的指标口径）
└─ scripts/              ← 算数的脚本
```

**注意**：`references/rules.closure.md` 是打包时自动生成的，**不要手改**。

---

## 三、为什么算数一定要用脚本？

让 AI 算"六个月平均收入"，它会：

- **算错**（AI 不擅长算术，尤其数字多了）
- **慢**（要一个字一个字生成）
- **贵**（生成数字也要花 token）

而 Python 脚本算这个，又快又准又免费。

**所以我们定的规矩是：凡是能用脚本算的，一律用脚本。AI 只做"判断"这种脚本做不了的事。**

**审核时要盯的三件事**：

2. `cond` 里用的变量，有没有在 `rules/dict.yaml` 里定义过（没定义会构建失败）
3. 等级定得合不合理（同一个现象，不能一条判"高"一条判"中"）

### 任务 2：写等级合成脚本

**做什么**：`skills/sk_rules/scripts/synthesize.py`

**为什么**：`sk_rules` 是**裁判**，负责把所有专家报上来的问题汇总成"这笔贷款整体是高/中/低风险"。

规则是这样的：

```
只要有一条"高风险"  →  整体判"高风险"
只有"中风险"没有"高" →  整体判"中风险"
只有"低风险"或啥都没  →  整体判"低风险"
同一个问题报了好几次  →  取最高的那个等级
两个专家结论打架      →  强制判"高风险"，并标注要人工复核
```

**为什么不直接让 AI 判断**：因为这是纯查表的事。让 AI 算，同一份数据跑两次**可能给出两个不同答案**。脚本就不会。

**怎么算做完**：

- [ ] 规则库 ≥ 200 条，`python build/pack.py` 通过
- [ ] 合成脚本对同一输入跑两次，结果**完全一致**

- **多头家数** = 在几家机构借了钱
- **总负债** = 各家余额加起来 + 对外担保

**为什么必须用脚本**：这是纯加减法。客户可能借了 8 家机构的钱，让 AI 一家家加，它会加错。

### 任务 3：补征信规则（13 → 40+）

**重点补这些现在缺的**：

| 缺什么           | 为什么重要                     |
| ------------- | ------------------------- |
| **担保圈**       | 给亲戚担保 30 万，这是隐性负债，现在完全没算  |
| **查询原因分布**    | 查征信的原因能看出他在急什么（贷款审批？信用卡？） |
| **近期新增贷款**    | 三个月内突然新增好几笔，说明资金链可能有问题    |
| **呆账 / 代偿记录** | 比逾期更严重                    |
| **失信被执行人**    | 一票否决项                     |
| **共同借款人负债**   | 夫妻共同借款，两边的负债都要算           |

**怎么算做完**：

- [ ] 《征信审查要点》有实质内容
- [ ] 脚本能正确算负债率/多头/总负债，有测试用例

## 钱浩军 · 出题与评测

### ⚠️ 你的第一条纪律

**造题期间，不许打开 `skills/` 文件夹，不许看任何 skill 是怎么写的。只能看赛题原文。**

**为什么**：自己想答案、自己出题，肯定全对。但那是在自己考自己，**毫无意义**。必须模拟"评委拿到一个我们从没见过的客户，来考我们"。

### 任务 1：造题

**做什么**：在 `eval/cases/` 下出题。

**题目长什么样**：一道题 = 一个客户的情况 + 问法。比如：

```
{
  "question": "帮我看下这个客户申请 10 万买农机，风险大不大？",
  "data": { 客户的材料、流水、征信... },
  "expected": { 应该识别出哪些风险点 }
}
```

**分三档出**：

| 档次          | 考什么                         | 数量建议                       |
| ----------- | --------------------------- | -------------------------- |
| **L1 单元题**  | 只考一个专家。比如只给流水，看能不能识别收入不稳    | 每题至少 1 个正例 + 1 个边界 + 1 个反例 |
| **L2 单环节题** | 一个环节里考多个能力。比如贷前要同时看材料+流水+征信 | 20-30 题                    |
| **L3 复合题**  | 跨环节、一次问好几件事                 | 15-20 题                    |

### 任务 2：藏起 20% 的题

**做什么**：出完题后，**挑 20% 藏起来，不给写 skill 的人看**。

**为什么**：如果出题人和写代码的人看同一套题，写的人会不自觉地"针对这些题"优化——这叫**过拟合**。等评委会出不一样的题，就露馅了。

藏起来的那 20%，只在最后验收时用。

### 任务 3：专门出"坑题"

**做什么**：出一些**故意让人误判**的题。

**为什么**：这是最容易发现问题的地方。

举例：

- 用户问的是**贷后**的事，但话里带着"材料"两个字 → 看主智能体会不会错误地去找材料专家
- 明明**季节性断档**是正常的，看成"经营中断"就是误报
- 数据里**缺少**关键字段 → 看系统会不会瞎猜（正确做法是标注"数据不全"，而不是硬给结论）

### 任务 4：写跑分脚本

**做什么**：`eval/runner.py`

**干什么**：把所有题跑一遍，记录

- 答案是**对**还是**错**
- 花了多少 token
- 花了多长时间

有了这个，才知道改一个东西是**变好了还是变坏了**。

**怎么算做完**：

- [ ] L1/L2/L3 题目齐了
- [ ] 20% 已标记为 held-out 并单独存放
- [ ] 有至少 10 道对抗性的坑题
- [ ] 跑分脚本能出报告
